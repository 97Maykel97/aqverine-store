# Стратегия тестирования AQVERINE

## Уровни и автоматический запуск

| Уровень | Что защищает | Команда |
| --- | --- | --- |
| Unit | расчёт корзины, цены, варианты, поиск и схемы форм | `npm run test:unit` |
| Integration | связь гостевой корзины с checkout и нормализация сохранённых данных | `npm run test:integration` |
| Component | реакции интерфейса на действия пользователя | `npm run test:component` |
| E2E | критические пользовательские пути в настоящем Chrome | `npm run test:e2e` |

`npm run test:run` запускает весь набор Vitest. GitHub Actions выполняет lint, typecheck, каждый уровень Vitest и E2E при push и pull request. E2E-команда собирает приложение и поднимает отдельный production-сервер на порту 3101. Все текущие сценарии работают с mock-каталогом и не требуют секретов или реальных персональных данных.

После первого создания тестового файла агент не меняет и не удаляет его самостоятельно. Существующие тесты используются только для проверки. При падении теста агент исследует причину и исправляет приложение; если неверен сам тест, сначала запрашивает явное разрешение пользователя на его изменение. Новые тестовые файлы допустимы для новых возможностей.

## Приоритетные E2E-сценарии текущего frontend

1. Поиск: пустой результат → подсказка товара → карточка найденного товара.
2. Товар и корзина: выбранные цвет и размер попадают в drawer; количество, удаление, итог и сохранение после перезагрузки работают на desktop и mobile.
3. Checkout: пустая корзина не позволяет перейти к форме; с товаром видны состав и сумма, форма валидируется и честно сообщает, что заказ и оплата не создаются.
4. Закрытый admin-маршрут: прямой переход на `/aqverine-control` ведёт на экран без административных действий. Это временный frontend-инвариант, **не проверка реальной ролевой защиты**.

## Добавить после готовности backend

- Supabase Auth: регистрация, вход, выход, восстановление доступа, защищённые cookies; гость не получает чужие данные.
- Серверная корзина: объединение с гостевой по `variantId`, ограничение остатком, синхронизация между устройствами.
- Заказ: серверная перепроверка цены и остатка, транзакционное создание `pending_payment`, сохранение снимка `OrderItem`, запрет оформления пустой корзины.
- Оплата: создание платежа через `PaymentProvider`, валидная и невалидная подпись webhook, повторная доставка события, `paid` только после webhook, отдельные `failed`, `cancelled` и `refunded`.
- Личный кабинет и admin API: видимость только собственных заказов; запрет доступа без роли `admin`; управление товарами, остатками и операционными статусами без изменения статуса оплаты из UI.

Эти проверки нельзя помечать как пройденные или заменять фиктивными backend-ответами до появления соответствующих серверных сценариев.
