# Платёжный поток

## Локальная проверка без реальной оплаты

Для разработки без Stripe задайте в `.env.local` `PAYMENT_PROVIDER=local`, `PAYMENT_LOCAL_SECRET` (случайная строка длиной не менее 32 символов) и `NEXT_PUBLIC_APP_URL=http://localhost:3000`. Режим работает только при `NODE_ENV=development` и только на `localhost` или `127.0.0.1`; в production он недоступен. Секрет не передаётся клиенту и не коммитится. PostgreSQL и Supabase Auth должны быть настроены, поскольку заказ и его владелец проверяются на сервере.

`POST /api/checkout` создаёт обычный заказ и резервирует остаток. `LocalPaymentProvider` возвращает подписанную HMAC-сессию для `/payment/demo`; страница доступна только владельцу заказа. Пользователь выбирает «оплата прошла», «платёж отклонён» или «отменить». `POST /api/payments/demo/complete` проверяет Origin, сессию, владельца, сумму и текущий статус, затем отправляет подписанное событие во внутренний `POST /api/payments/webhook`. Только обработчик webhook меняет `Payment` и `Order`; повторное событие имеет тот же ID и не создаёт второй заказ. При отказе или отмене резерв освобождается. Защищённое задание закрытия старых платежей также отправляет событие `cancelled` через webhook. Карта и CVV нигде не вводятся; деньги не списываются. Такой результат подтверждает работу локального сценария, а не приём Visa/Mastercard.

## Stripe Checkout в тестовом режиме

```text
Checkout авторизованного покупателя
-> сервер проверяет корзину, цены и остатки в транзакции Serializable
-> сервер резервирует остатки и создаёт Order со статусом pending_payment, snapshot OrderItem и Payment
-> StripePaymentProvider создаёт тестовую Stripe Checkout Session для карт Visa/Mastercard
-> пользователь переходит на защищённую страницу Stripe
-> Stripe отправляет webhook
-> сервер проверяет подпись по raw body и PAYMENT_WEBHOOK_SECRET
-> сервер идемпотентно обновляет Payment и Order
-> страница возврата читает статус заказа через защищённый API покупателя
```

`POST /api/checkout` принимает Zod-проверенные контакты и UUID `idempotencyKey`. Повтор с тем же ключом возвращает существующую открытую Stripe Session, если она ещё доступна. Создание Stripe Session использует ID платежа как ключ идемпотентности провайдера. Для тестового режима требуются `PAYMENT_PROVIDER_SECRET_KEY=sk_test_...`, `PAYMENT_WEBHOOK_SECRET=whsec_...`, `NEXT_PUBLIC_APP_URL` и действующая конфигурация PostgreSQL/Supabase. Значения ключей не помещаются в Git.

После подписанного события `checkout.session.expired` или `checkout.session.async_payment_failed` заказ становится отменённым, а резерв товара освобождается. Владелец может вызвать `POST /api/account/orders/[orderId]/retry-payment` с новым UUID `idempotencyKey`: сервер проверяет статус последнего платежа, наличие товара и соответствие текущих цен исходному snapshot, повторно резервирует остаток в транзакции и создаёт новый `Payment` для того же `Order`. Повтор запроса с тем же ключом возвращает открытую сессию. При изменении цены или отсутствии товара нужно оформить новый заказ.

Webhook принимает только подписанное событие Stripe. `checkout.session.completed` помечает заказ оплаченным лишь при `payment_status=paid`; `checkout.session.async_payment_failed` и `checkout.session.expired` переводят его в неуспешное или отменённое состояние и возвращают зарезервированный остаток; полное `charge.refunded` переводит оплаченный заказ в `refunded`. `PaymentWebhookEvent` хранит уникальный `(provider, providerEventId)`, поэтому повтор события не повторяет переход и не создаёт новый заказ. Подпись, сумма, валюта, ID платежа и допустимость перехода проверяются до изменения заказа.

Провайдерские ключи, webhook secret, PAN и CVV остаются только на сервере. Невалидная подпись получает `401` или `403`. Страница возврата не меняет платёжный статус: она показывает текущий статус из `GET /api/account/orders/[orderId]` только владельцу заказа и повторно запрашивает ожидающий статус.

Защищённый `POST /api/internal/payments/expire-stale` принимает `Authorization: Bearer <CRON_SECRET>`. Его должен вызывать внешний планировщик. Задание просматривает до 100 последних `PENDING` платежей с сохранённым Stripe Session ID, которые не обновлялись 25 минут, и запрашивает закрытие только ещё открытых сессий провайдера. Оно возвращает только агрегированные счётчики и **не меняет** `Payment`, `Order` или остаток: это делает только подписанный `checkout.session.expired` webhook. Если webhook не доставлен, резерв остаётся до повторной доставки события или ручной диагностики; повторную доставку Stripe и состояние зависших заказов нужно мониторить. Платежи без сохранённого Stripe Session ID требуют отдельной диагностики и не закрываются этим заданием. При backlog более 100 платежей старые записи могут не попасть в очередной запуск: для боевой эксплуатации нужны мониторинг backlog и постраничная обработка.
