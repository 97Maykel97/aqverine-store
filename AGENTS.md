## Обязательное чтение документации

- Перед изменением архитектуры прочитайте `docs/architecture.md`.
- Перед изменением схемы БД прочитайте `docs/db-schema.md`.

## Условия завершения

- После задачи обновите `docs/progress.md`: выполненная работа, файлы и новые env-переменные.
- При изменении БД обновите `docs/db-schema.md`.
- Перед передачей существенных изменений выполните `npm run lint`, `npm run typecheck`, `npm run test:run` и `npm run build`.
- Для изменений интерфейса запустите проект и проверьте сценарий в браузере.

## Жизненный цикл Git-задачи

Применяйте этот порядок к каждой новой фиче, рефакторингу и исправлению бага, включая работу субагентов.

### 1. Инициализация и изоляция

- Никогда не пишите код напрямую в защищённых ветках: `main`, `master` или `dev`.
- До разработки прочитайте `docs/git-flow.md`, если файл существует, и следуйте его стандартам веток, коммитов и префиксов. Иначе используйте имена вроде `feature/<task-name>` или `fix/<task-name>`.
- При параллельной работе субагентов или другого процесса в репозитории используйте отдельный Git worktree для каждого процесса.
- При последовательной работе создайте ветку задачи: `git checkout -b <branch-name>`.

### 2. Разработка и точки сохранения

- Работайте только в выбранной ветке или worktree.
- После каждого крупного завершённого блока (схема данных, контроллер, протестированная фича) создавайте атомарный промежуточный коммит.
- Создавайте такие коммиты автоматически по соглашению проекта, не ожидая подтверждения пользователя.

### 3. Завершение и ревью

- Когда все требования реализованы и проверены, остановитесь и создайте финальный коммит в ветке задачи.
- Кратко сообщите изменённые файлы и добавленную функциональность.
- For sequential work, end with: “Фича реализована. Проверяем работу, или я могу выполнить слияние (merge) с главной веткой?”
- For isolated parallel work, end with: “Изолированная работа завершена. Могу ли я слить ветку в main и удалить временный worktree?”
- Never run `git merge`, delete a worktree, or create a pull request without explicit user authorization: “Да, сливай”.

# Тестирование

При создании нового функционала создавай только самые важные unit, integration и component тесты.
При редактировании уже существующего функционала, тесты редактировать нельзя.
